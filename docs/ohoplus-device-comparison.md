# CHO 与 OHO++ 实机对照

2026-11-15。比较 CHO 0.4.1（28）和 [OHO++ 1.0.6（7）](https://github.com/contenere-cos/OHOPlus/releases/tag/v1.0.6-vc7)，设备为一加 PKR110，系统为 `PKR110_17.0.0.101(CN01)` / Android 17。OHO++ APK 的 SHA-256 为 `87fab786d4b3dd5b085ebad67de528a9eee1a8e932d40694c2a354fa8ab4dc95`，与发布附件一致。

本次最有用的结论是：让手势运行在 SystemUI 中，确实可以在主应用被划掉后继续打开部分工具；但输入接口、窗口内容所属进程、后台启动和 Root 通道都需要分别验证。CHO 的小组件尺寸适配和窗口点击规则也有实际价值，不适合整套替换。

## 测试条件

- 机主已暂时移除 CHO 的系统应用属性。实机包标志不包含 `SYSTEM` 或 `UPDATED_SYSTEM_APP`，没有改包名、版本、签名或配置。
- 测试前 CHO 的无障碍服务已关闭，其余服务保留原状态。交互测试期间临时启用 CHO，并保留其他服务。
- 手机已有其他系统模块。本次没有逐个关闭它们，因此这是当前设备组合下的结果，不是隔离环境中的通用兼容性排名。
- OHO++ 从未安装的状态开始，启用 LSPosed API 102 模块。先重载 SystemUI，再完整重启；日志确认 `system_server` 和 SystemUI 均加载。不能把前一阶段缺少框架加载的结果当成最终结果。
- OHO++ 应用端曾获“到本次重启”为止的临时 Root，用于保存初始配置；完整重启后该授权到期，没有再次授权。重启后的受控配置由 ADB Root 写入并读回。涉及应用自身 Root 辅助进程的功能不能视为在持续授权条件下完成验收。SystemUI 找不到 `su` 是另一个进程中的直接日志证据。
- 手机管家对 OHO++ 显示风险提醒，测试时选择“继续使用”，没有关闭检测或选择“不再提醒”。本次不是恶意软件审计，不据此断言其含有恶意行为。
- OHO++ 使用受控测试配置：左右短直滑为返回，长上斜滑为小组件、长下斜滑为快速工具；横竖屏触区名义宽度均为 11dp。主测试关闭预测式返回，另外保留开启时的失败记录。安装器、桌面布局、通知蒙版、分屏等扩展未开启。
- CHO 沿用机主动作配置，只在横屏测试时临时关闭“横屏模式下隐藏触钮”。该选项原本开启，最早一轮横屏结果只用于确认原设置，不计作触区测试。
- 点击和滑动由 ADB 注入到实机，结合前台 Activity、窗口、提供方内容、日志和截图判断结果。不是纯离线模拟，也不是人工握持测试。
- 临时测试应用提供左右边缘按钮、点击计数和输入框。它的返回回调没有按预期计数，故返回成功以测试 Activity 是否退出为准，不以 `backs=0` 判断失败。

“划掉最近任务”与“直接杀进程”的差别已实测，后续保活工作必须分别验收。本轮没有用 `am force-stop` 替代这两项测试。

OHO++ 的小组件依然依赖应用进程：划掉主应用后，手势能发起小组件服务请求，但该次服务记录中的 `app` 为 null；重新打开 OHO++ 后可以显示小组件弹窗。后续日志还记录了 ColorOS 对应用进程的冻结。冻结与长按无响应存在时间上的关联，但没有单独排除输入转发、坐标和启动限制，不能认定冻结是唯一原因。

支付宝绑定后的流程出现过账号登录和指纹界面，均已取消或离开，没有登录、验证身份或操作付款。最终确实创建了单独的小组件实例并取得提供方内容；不能将登录页面误记为绑定失败。CHO 原有实例没有移交给 OHO++。

## 与实现对应的故障点

**返回和输入接口。** 日志中的方法缺失包括 `EdgeBackGestureHandler.onInputEvent$1`、`OplusNavBarUtils.isSupportGestureSideBar` 和 `BackAnimationController.onMotionEvent`。部分 Hook 成功不代表完整输入链路可用。

OHO++ 的普通按键注入反射调用 `InputManager.getInstance()`。实机只查到了 `InputManagerGlobal.getInstance()`，同时可以查到两类上的注入方法。结合返回识别成功但未退出的结果，这是明确需要排查的接口差异；本次没有修改其 APK 验证修复，故不将其称为全部返回问题的唯一根因。

**Root 的执行位置。** 触控板的日志直接报 `Cannot run program "su": error=2, No such file or directory`，调用发生在 SystemUI 进程。给 OHO++ 应用授权 Root，不会自动保证另一个进程中的可执行文件可见性、身份和环境一致。后续应由明确的特权辅助进程提供有限操作接口，再验证实际设备注册和输入效果。

**原生视图与自绘面板。** 原生侧滑视图的复用、系统窗口托管和自绘 RuntimeShader 是不同层次。OHO++ 面板能进入、退出，不能证明背景捕获已经成功；得到一个窗口 Binder，也不能证明 AppWidget 内容进程不会冻结。

**小组件尺寸。** OHO++ 的网格直接约束 AppWidgetHostView；本次支付宝 4×2 的实际裁切与此前 CHO 的固定内容问题相似。CHO 保留 `SizedWidgetHostView` / `WidgetContentFit` 的内容适配，并按实际内容盒报告尺寸。这项不应随窗口后端更换而丢失。

**退场录屏。** 两段录屏均使用相同测试页、正常系统动画倍率。按稳定面板与关闭后画面的灰度差投影，OHO++ 和 CHO 分别取得 7、11 个处于 10%–90% 之间的退场样本。两者形变和材质不同，采样结果只证明本次存在连续退场，不用于判断谁更流畅或制定新的 ColorOS 动画时长。

## 对 CHO 的采用建议

1. 先做小范围可选 LSPosed 后端，复用现有 `GestureRecognizer` 和动作配置，分别抽离输入、动作执行与窗口宿主。首先证明普通点击、返回提交、取消和恢复正确，再接完整工具。
2. 每项能力都做实际调用和结果验证。发现接口不支持时保留原有输入或说明该功能不可用；不要提前截断系统手势，再让后续动作静默失败。
3. 特权能力在固定进程中管理。手势识别留在系统侧，不把 Root 命令、提供方配置和所有工具业务一起放进 SystemUI。
4. 跨进程窗口需同时验证内容进程冻结、死亡、IME、输入坐标和关闭顺序。单独处理“系统窗口还在、内容服务没了”的状态。
5. 保留 CHO 的组件尺寸适配、自动轮播、提供方配置恢复和各类窗外点击规则。后台后端变化不能成为重写这些已验收行为的理由。
6. 原生预测式返回、系统鼠标和胶囊形变可分别作为后续能力；本轮不能把 OHO++ 在本机未通过的路径当成可直接采用的成品。

本次没有实现 Shizuku 恢复或 LSPosed 后端，也没有修改 CHO 的功能代码。长期后台、耗电、其他固件、系统清理按钮、全部动作、其他系统模块的独立影响，以及完整鼠标点击/拖动仍未验收。
